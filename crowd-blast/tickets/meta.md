# Tickets META (rôle META : `src/meta/`, `src/ui/`, tests dans `tests/meta/` et `tests/ui/`)

Stack : JavaScript pur en modules ES, DOM + CSS pour l'UI, `localStorage` (clé `SAVE_KEY` de `src/constants.js`, soit `crowdblast.save.v1`), tests avec le testeur intégré de Node. Aucune dépendance, aucun build. Le jeu est 100 % local : **aucune pub, aucun achat, aucun classement, aucune énergie, aucun réseau** (SPEC §0 et §3). Tous les textes affichés sont en **anglais**.

Conventions communes à tous les tickets :
- Imports relatifs avec extension `.js` obligatoire (modules ES natifs). Typage par JSDoc ; `src/contracts.d.ts` n'est jamais importé à l'exécution.
- Tout `src/meta/*` (sauf l'adaptateur `localStorage` par défaut) est de la logique pure : aucun accès à `window`, `document` ni `localStorage` global. Le temps (`clock.now()`), l'aléa (`rng()`) et le stockage (`storage`) sont injectés. Les tests utilisent une horloge factice, un RNG seedé et un faux `localStorage` en mémoire (`tests/meta/helpers.js`, créé par META-1).
- Le code d'UI (`src/ui/*`) est vérifié visuellement (serveur statique + navigateur mobile ou émulé). Toute logique non triviale de l'UI (formatage, libellés, calcul d'état de boutons) est extraite dans des modules purs (`src/ui/format.js`, `src/ui/strings.js`, `src/ui/viewmodels.js`) testables sous Node.
- Commandes : tout le projet `node --test` ; tests META `node --test tests/meta/*.test.js` ; tests UI purs `node --test tests/ui/*.test.js`. Ne jamais passer un dossier en argument (`node --test tests/` échoue sur Node 22). Vérification visuelle : `python3 -m http.server 8000` à la racine du dépôt, puis `http://localhost:8000/src/ui/preview.html` (page d'aperçu de META-10) ou `http://localhost:8000/`.
- Aucun nombre d'équilibrage hors de `src/meta/balance.js`.
- Ordre critique : META-1 > META-2 > META-3 > META-4 > META-9 > META-10 > META-11 > META-12 > META-16. META-5 à META-8 s'insèrent avant META-9 ; META-13 à META-15 après META-11.
- Jalons (SPEC §8) : M2 = META-1 à META-13 ; M3 = META-14 à META-16.

### META-1 : Socle méta (horloge, RNG, stockage, balance, aides de test)
- Priorité : P0
- Dépend de : aucun
- Description : Dans `src/meta/` : `clock.js` (`systemClock = { now: () => Date.now() }`, `createFakeClock(start)` avec `advance(ms)` et `set(ms)`), `rng.js` (`createRng(seed)` mulberry32 renvoyant une fonction `() => [0,1[`), `storage.js` (`createSafeStorage(raw?)` : enveloppe tout accès `getItem/setItem/removeItem` dans un try/catch ; si `localStorage` est absent ou lève (navigation privée, quota), bascule sur un stockage mémoire et expose `isPersistent()`), `balance.js` (toutes les constantes d'équilibrage : coûts d'atelier, multiplicateurs, table d'XP, niveaux de déblocage des armes, catalogue de missions, bornes de coffre, `REVIVE_COST = 100`, effets affichés des améliorations). Créer `tests/meta/helpers.js` : `createFakeLocalStorage()` (API `getItem/setItem/removeItem/clear`, option `failWrites` pour simuler un quota dépassé) et `makeEnv()` renvoyant `{ clock, rng, storage }` prêts à l'emploi. Ajouter une fonction pure `localDayKey(now, offsetMinutes = new Date(now).getTimezoneOffset())` renvoyant `YYYY-MM-DD` (le décalage est injectable pour tester sans dépendre du fuseau de la machine).
- Critères d'acceptation :
  - `node --test tests/meta/foundation.test.js` passe : horloge factice qui avance, RNG seedé reproductible (même seed => mêmes 20 valeurs, toutes dans [0,1[), seeds différentes => séquences différentes, stockage sûr qui bascule en mémoire quand `setItem` lève, `localDayKey` correct pour 23:59:59 et 00:00:01 avec un décalage fixe de -120 min.
  - `balance.js` exporte `REVIVE_COST === 100` ; un test le compare à SPEC.md §3.
  - `grep -rn "Date.now\|Math.random" src/meta` ne renvoie que `clock.js` (et aucun autre fichier).
  - `grep -rn "localStorage" src/meta` ne renvoie que `storage.js`.
  - `grep -rniE "energy|energie|advert|rewarded|interstitial|iap|leaderboard|noAds" src/meta src/ui` ne renvoie rien (périmètre sans pub, achat ni énergie).
- Interfaces utilisées / fournies : utilise `SAVE_KEY` (`constants.js`). Fournit des utilitaires internes à `src/meta/`.

### META-2 : SaveService (localStorage, valeurs par défaut, migration de version)
- Priorité : P0
- Dépend de : META-1
- Description : `src/meta/save.js` : `createLocalSaveService({ storage, clock })` conforme à `SaveService`. Clé `SAVE_KEY`. `load()` sans donnée : `defaultSave()` (thème `zombies`, arme `starter` débloquée et sélectionnée, niveau 1, XP 0, pièces 0, améliorations à 0, réglages `sfx/music/haptics` à vrai, `gore: 'soft'`, `colorblind: false`, missions vides avec `day: ''`, coffres vides, `bestDistanceByTheme` vide). La forme est exactement celle de `SaveData` dans `contracts.d.ts` (aucun champ d'énergie, de pub, d'achat ni de minuteur). JSON illisible : copie de la valeur brute sous `SAVE_KEY + '.corrupt'`, retour des valeurs par défaut. Pipeline de migration `migrate(raw)` par étapes `vN -> vN+1` (étape `v0 -> v1` pour un objet sans champ `version` ou aux champs manquants ; les champs inconnus ou obsolètes, par exemple `energy`, sont ignorés). Version supérieure à 1 : ne pas écraser, copie sous la clé `.corrupt`, valeurs par défaut en mémoire uniquement. Assainissement après migration : champs manquants complétés par les défauts, nombres bornés (pièces >= 0, améliorations dans [0,5]), valeurs d'enum invalides (thème, arme, gore) remplacées par les défauts, `unlockedWeapons` contient toujours `starter`, `selectedWeapon` appartient à `unlockedWeapons`. `save(data)` : exception d'écriture (quota) capturée, jamais propagée, cache mémoire pour que `load()` renvoie la dernière valeur. `reset()` supprime la clé. `load()` renvoie toujours une copie profonde (muter le résultat ne modifie pas le cache).
- Critères d'acceptation : `node --test tests/meta/save.test.js` passe, couvrant : premier lancement (valeurs par défaut exactes), aller-retour `save`/`load` identique, JSON invalide (défauts + clé `.corrupt` présente), migration de `{ coins: 120 }` sans version vers v1 avec compléments, présence d'un champ obsolète `energy` ignorée sans erreur, version 2 non écrasée, enums invalides corrigés, valeurs négatives ou hors bornes bornées, écriture qui lève (aucune exception, `load()` suivant renvoie la dernière sauvegarde), `reset()`, copie profonde. Un test vérifie que `defaultSave()` contient exactement les clés de `SaveData` de `contracts.d.ts` (liste de clés attendue écrite dans le test).
- Interfaces utilisées / fournies : fournit `SaveService` ; utilise `SaveData`, `Settings`, `SAVE_KEY`.

### META-3 : Cœur du compte (pièces, réanimation, XP, niveau, record, réglages, `applyRunResult`)
- Priorité : P0
- Dépend de : META-2
- Description : Module `src/meta/account.js` (fonctions pures sur un `SaveData` + enveloppe de persistance). `applyRunResult(result, themeId)` : pièces créditées = `result.coinsEarned` (valeur finale fournie par le moteur, incluant le bonus de boss), arrondie à l'entier et bornée à 0 ; XP gagnée = `10 + floor(distanceM / 20) + 5 * bossesDefeated + floor(kills / 10)` ; XP cumulée nécessaire au niveau L = `50 * L * (L - 1)` (niveau 2 à 100, niveau 3 à 300, niveau 4 à 600), niveau maximal 30 ; record par thème mis à jour si `distanceM` est strictement supérieur à l'ancien (`newRecord` ; sans record antérieur, toute distance > 0 est un record) ; `newLevel` non nul uniquement à la montée de niveau (peut sauter plusieurs niveaux). `result.endedBy === 'quit'` : pièces, XP et record accordés normalement. Valeurs invalides (NaN, négatives, absentes comme `noDamageDistanceM`) traitées comme 0 sans exception. Les champs `chestEarned`, `missionsCompleted`, `unlockedWeapons` du `RunSummary` sont remplis par META-5, 6, 7 ; ici ils valent `null`, `[]`, `[]`. Aussi : `addCoins(amount)` (entier >= 0, ignore les valeurs invalides), `spendCoins(amount)` (entier > 0 ; `false` sans effet si le solde est insuffisant ou si la valeur est invalide ; sinon débit et `true`), `getReviveCost()` (renvoie `REVIVE_COST` de `balance.js`), `updateSettings(patch)` (fusion partielle, validation des enums et booléens, persistance), `onSettingsChanged(cb)` (liste d'abonnés, chaque appel de `updateSettings` notifie avec une copie des réglages complets ; un abonné qui lève n'empêche pas les autres), `selectTheme(id)` (refuse les ids inconnus, persiste). Le niveau stocké est recalculé depuis l'XP au chargement s'ils divergent.
- Critères d'acceptation : `node --test tests/meta/account.test.js` passe : XP sur 3 jeux de valeurs chiffrés ; 99 XP => pas de montée, 100 XP => `newLevel === 2` ; saut de plusieurs niveaux ; niveau plafonné à 30 ; record par thème indépendant (record zombies sans effet sur cyber) ; `newRecord` faux à distance égale ; résultat NaN/négatif/champs absents sans exception ; `addCoins(NaN)` et `addCoins(-5)` sans effet ; `spendCoins(100)` avec 99 pièces => `false` et solde inchangé, avec 100 pièces => `true` et solde 0, `spendCoins(0)` et `spendCoins(-5)` => `false` ; `getReviveCost() === 100` ; `updateSettings({ gore: 'x' })` ignoré ; `updateSettings` notifie une fois avec l'objet complet ; un abonné qui lève n'empêche pas le suivant ; `selectTheme('inconnu')` ignoré.
- Interfaces utilisées / fournies : `applyRunResult`, `addCoins`, `spendCoins`, `getReviveCost`, `updateSettings`, `onSettingsChanged`, `selectTheme`, `getSave` de `MetaService` ; utilise `RunResult`, `RunSummary`, `Settings`, `ThemeId`.

### META-4 : Atelier (courbe de coûts) et `buildRunConfig`
- Priorité : P0
- Dépend de : META-3
- Description : Module `src/meta/workshop.js`. Coût du passage du niveau n au niveau n+1 (n de 0 à 4) = `BASE[n] * MULT[id]` arrondi au multiple de 5 supérieur, avec `BASE = [50, 120, 260, 520, 1000]` et `MULT = { fire_rate: 1.0, damage: 1.0, crowd_start: 1.2, coin_magnet: 0.8 }`. `getUpgradeCost(id)` renvoie `null` au niveau 5. `buyUpgrade(id)` : refus (`false`, état inchangé) si pièces insuffisantes, niveau maximal ou id inconnu ; sinon débit et incrément. `buildRunConfig(theme, seed)` : `{ theme, weaponId: arme sélectionnée, upgrades: copie, seed: seed >>> 0, tutorialSafeZone: true, gore, colorblind }` issus de la sauvegarde. - Critères d'acceptation : `node --test tests/meta/workshop.test.js` passe : table complète des 20 coûts attendus (4 améliorations x 5 niveaux) vérifiée valeur par valeur ; coûts strictement croissants par amélioration ; `null` au niveau 5 ; 49 pièces au coût 50 => refus sans débit, 50 pièces => achat et solde 0 ; aucun achat au niveau maximal ; `buildRunConfig` renvoie des améliorations indépendantes de la sauvegarde (muter la config ne modifie pas `getSave()`), `seed` converti en entier non signé (`-1` devient `4294967295`), `tutorialSafeZone === true`, gore et daltonisme issus des réglages ; `describeUpgrade('crowd_start', 2).current` correspond à « 3 shooters at start ».
- Interfaces utilisées / fournies : `getUpgradeCost`, `buyUpgrade`, `buildRunConfig` ; utilise `RunConfig`, `UpgradeId`, `UpgradeLevels`, `ThemeDef`.

## Hypothèses

1. Tests : fichiers `tests/meta/*.test.js` et `tests/ui/*.test.js` (propriété META) ; faux `localStorage` dans `tests/meta/helpers.js`. L'UI DOM n'est pas testée automatiquement (pas de jsdom) ; seule la logique extraite (`format.js`, `strings.js`, `viewmodels.js`) et l'audit CSS le sont.
2. Valeurs d'équilibrage META (modifiables dans `balance.js`) : coûts d'atelier `[50, 120, 260, 520, 1000]` multipliés par `fire_rate` 1,0, `damage` 1,0, `crowd_start` 1,2, `coin_magnet` 0,8, arrondis au multiple de 5 supérieur ; XP par run `10 + floor(distance/20) + 5 x boss + floor(kills/10)` ; XP cumulée au niveau L `50 x L x (L - 1)`, niveau maximal 30 ; armes débloquées aux niveaux 1/2/4/6/8 ; coffre si distance >= 150 m ou au moins 1 boss vaincu, quel que soit `endedBy`, plafond de 4 coffres non ouverts ; contenu d'un coffre 80 à 200 pièces tirées à l'ouverture ; missions : kills 50/150/300, distance 500/1000/2000 m, boss 1/2, sans dégât 200/400 m ; réanimation : 100 pièces fixes, décompte de 8 s, foule de 5 tireurs (valeur imposée par le moteur).
3. Les missions et le reset suivent le jour local de l'appareil ; un changement de fuseau ou une horloge système modifiée peut les régénérer. Accepté en v1 (pas d'horloge serveur).
4. Les quatre missions progressent après toute fin de run, y compris `quit` (les boss vaincus avant l'abandon comptent), car le résultat reflète des faits de jeu réels.
5. Le niveau stocké est dérivé de l'XP ; en cas de divergence au chargement, l'XP fait foi.
6. Les textes de l'interface sont en anglais seulement, centralisés dans `strings.js`. Le mode daltonien de l'UI ajoute icônes et textes ; les palettes du canvas relèvent du moteur et de CONTENT.
7. Budget : META vise moins de 60 Ko non compressés pour `src/meta/` et `src/ui/` (hors CSS), aucun asset binaire, aucune police externe (polices système).
8. Le test d'accessibilité CSS est une approximation (expressions régulières sur la feuille de style) ; la conformité réelle des zones tactiles est confirmée en vérification visuelle à 360x640 et 390x844.
9. Préfixe des classes CSS et des variables : `cb-` (Crowd Blast).
